# Phase 3: MCP Server + Memory Reconciliation

Phase 3 adds an MCP server and a durable memory reconciliation layer.

The key design principle:

```text
MCP exposes simple cognitive actions.
The backend owns memory policy, learning, contradiction handling, lifecycle updates, and relation tracking.
```

So MCP should **not** expose low-level operations like `force_remember`, `propose_memory`, `learn_update`, or `deprecate_memory`.

Instead, expose four tools:

```text
recall_memory
record_interaction
submit_memory
memory_stats
```

---

# Final MCP Tool Surface

## 1. `recall_memory`

```python
recall_memory(
    query: str,
    namespace: str,
    top_k: int | None = None,
    include_hebbian: bool = True,
)
```

Use when the agent needs relevant memory.

This wraps the existing Phase 2 recall pipeline:

```text
hybrid retrieval

→ LiteLLM rerank
→ activation scoring
→ diversity filtering
→ Hebbian spreading
→ reinforcement
```

The HTTP endpoint can remain `/recall`, but the MCP tool should be named `recall_memory` because it is clearer for agents.

raw user/assistant exchange

# Core Concept: Memory Reconciliation

The main new internal service is:

```text
MemoryReconciliationService
```

It owns `submit_memory`.

Flow:

```text
submit_memory
→ validate input
→ recall related memories
→ classify relationship between new content and existing memories
→ decide lifecycle action
→ create/reinforce/supersede/deprecate/refine/keep both
→ create semantic memory_relations
→ return transparent report
```

This is your lightweight belief-revision layer.

# Contradiction-Aware Classification

The classifier should not treat contradiction as automatic replacement.

Important rule:

```text
When memories conflict, first try to contextualize.
Only supersede when replacement is explicit.
```

Contradictions can arise because of:

```text
different time
different project
different namespace
different environment
different scope
different module
different technology generation
different user preference over time
```

So every classification should include:

```text
relation
confidence
contradiction_type
resolution
rationale
old_memory_refinement
new_memory_refinement
```

# Updated Relationship Classifier Prompt

Use this prompt inside `LiteLLMService.classify_memory_relationships`.

```text
You are reconciling a new memory candidate against existing memories.

Your job is not only to detect contradiction, but to diagnose whether an apparent contradiction can be resolved by context, time, scope, environment, or specificity.

Classify how the new content relates to each existing memory.

Allowed relation labels:
- confirms
- extends
- contradicts
- supersedes
- forgets
- unrelated
- duplicate

Definitions:
- confirms: new content supports the old memory.
- extends: new content adds compatible detail.
- contradicts: new content conflicts with the old memory, but both may still be valid under different contexts.
- supersedes: new content clearly replaces the old memory with a newer or more correct version.
- forgets: new content is an instruction to stop using the old memory.
- duplicate: new content says substantially the same thing.
- unrelated: no meaningful relation.

When relation is "contradicts", diagnose the contradiction carefully.

Allowed contradiction_type values:
- none: no contradiction.
- direct_conflict: both memories cannot be true at the same time in the same context.
- temporal_shift: the newer memory reflects a change over time.
- context_shift: both may be true in different projects, namespaces, sessions, users, modules, or contexts.
- scope_mismatch: one memory is broad and the other is narrower or more specific.
- environment_difference: both may be true in different environments such as local, staging, production, testing, frontend, backend, CLI, or deployment.
- preference_change: the user preference changed.
- implementation_change: the system, architecture, library, or technology choice changed.
- ambiguous: there is not enough information to decide.

Allowed resolution values:
- keep_both: both memories should remain active because they apply in different contexts.
- supersede_old: the old memory should be marked superseded by the new one.
- deprecate_old: the old memory should no longer be used.
- refine_old: the old memory should remain but should be narrowed or qualified.
- create_exception: the new memory should be stored as an exception to the old memory.
- needs_review: the system should not automatically modify the old memory.

Important rules:
- Do not mark an old memory superseded merely because there is a surface-level conflict.
- Prefer keep_both, refine_old, or create_exception when the conflict may be contextual.
- Use supersede_old only when the new content clearly says the old memory is outdated, replaced, or wrong.
- Use deprecate_old when the new content explicitly says to forget, stop using, or invalidate the old memory.
- If the new memory mentions words like "now", "no longer", "instead of", "migrated", "switched", or "going forward", consider temporal_shift or implementation_change.
- If the two memories refer to different projects, namespaces, modules, environments, or scopes, prefer context_shift, environment_difference, or scope_mismatch.
- Preserve both memories when they can be made true with contextual qualifications.

Intent: {intent}

New content:
{new_content}

Existing memories:
{numbered list}

Return only valid JSON in this shape:
[
  {
    "index": 0,
    "relation": "contradicts",
    "confidence": 0.86,
    "contradiction_type": "environment_difference",
    "resolution": "keep_both",
    "rationale": "The old memory says Redis is used in production caching, while the new memory says local tests use in-memory caching. These can both be true in different environments.",
    "old_memory_refinement": "Redis is used for production caching.",
    "new_memory_refinement": "Local tests use in-memory caching."
  }
]
```

For non-contradictions, still include all fields:

```json
{
  "index": 0,
  "relation": "duplicate",
  "confidence": 0.92,
  "contradiction_type": "none",
  "resolution": "keep_both",
  "rationale": "The new memory repeats the same project decision.",
  "old_memory_refinement": null,
  "new_memory_refinement": null
}
```

# `submit_memory` Decision Logic

The reconciliation service should use both:

```text
relation
resolution
```

not relation alone.

Decision table:

| Classification                                | Backend action                                                                                             |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `intent == "forget"`                          | Deprecate best matching related memory/memories. Do not create new memory unless no related memory exists. |
| `duplicate` with confidence ≥ 0.8             | Reinforce old memory. Do not create duplicate.                                                             |
| `confirms` with confidence ≥ 0.8              | Reinforce old memory. Usually do not create new memory.                                                    |
| `extends` with confidence ≥ 0.7               | Create new memory. Create relation `extends`.                                                              |
| `forgets` with confidence ≥ 0.7               | Deprecate matching old memory.                                                                             |
| `contradicts` + `resolution=keep_both`        | Create new memory. Keep old active. Create relation `contradicts`.                                         |
| `contradicts` + `resolution=refine_old`       | Create new memory. Keep old active. Create relation `refines`.                                             |
| `contradicts` + `resolution=create_exception` | Create new memory. Keep old active. Create relation `exception_to`.                                        |
| `contradicts` + `resolution=supersede_old`    | Create new memory. Mark old as `superseded`. Create relation `supersedes`.                                 |
| `contradicts` + `resolution=deprecate_old`    | Create new memory if useful. Mark old as `deprecated`.                                                     |
| `contradicts` + `resolution=needs_review`     | Create new memory with lower confidence. Keep old active. Create relation `contradicts`.                   |
| `supersedes` with confidence ≥ 0.7            | Create new memory. Mark old as `superseded`. Create relation `supersedes`.                                 |
| No meaningful relation                        | Create new memory.                                                                                         |

Important:

```text
contradicts does not automatically mean supersede
```

You are reconciling a new memory candidate against existing memories.

Allowed relation labels:

Definitions:
- confirms: new content supports the old memory.
- extends: new content adds compatible detail.
- contradicts: new content conflicts with the old memory, but both may still be valid under different contexts.
- supersedes: new content clearly replaces the old memory with a newer or more correct version.
- forgets: new content is an instruction to stop using the old memory.
- duplicate: new content says substantially the same thing.
- unrelated: no meaningful relation.

When relation is "contradicts", diagnose the contradiction carefully.

Allowed contradiction_type values:
- none: no contradiction.
- direct_conflict: both memories cannot be true at the same time in the same context.
- temporal_shift: the newer memory reflects a change over time.
- context_shift: both may be true in different projects, namespaces, sessions, users, modules, or contexts.
- scope_mismatch: one memory is broad and the other is narrower or more specific.
- environment_difference: both may be true in different environments such as local, staging, production, testing, frontend, backend, CLI, or deployment.
- preference_change: the user preference changed.
- implementation_change: the system, architecture, library, or technology choice changed.
- ambiguous: there is not enough information to decide.

Allowed resolution values:
- keep_both: both memories should remain active because they apply in different contexts.
- supersede_old: the old memory should be marked superseded by the new one.
- deprecate_old: the old memory should no longer be used.
- refine_old: the old memory should remain but should be narrowed or qualified.
- create_exception: the new memory should be stored as an exception to the old memory.
- needs_review: the system should not automatically modify the old memory.

Important rules:
- Do not mark an old memory superseded merely because there is a surface-level conflict.
- Prefer keep_both, refine_old, or create_exception when the conflict may be contextual.
- Use supersede_old only when the new content clearly says the old memory is outdated, replaced, or wrong.
- Use deprecate_old when the new content explicitly says to forget, stop using, or invalidate the old memory.
- If the new memory mentions words like "now", "no longer", "instead of", "migrated", "switched", or "going forward", consider temporal_shift or implementation_change.
- If the two memories refer to different projects, namespaces, modules, environments, or scopes, prefer context_shift, environment_difference, or scope_mismatch.
- Preserve both memories when they can be made true with contextual qualifications.
