## Reciprocal Rank Fusion

Implement:

```python
def reciprocal_rank_fusion(
    vector_results: list[tuple[Memory, float]],
    text_results: list[tuple[Memory, float]],
    *,
    rrf_k: int,
    limit: int,
) -> list[Candidate]:
    ...
```

Behavior:

1. Treat the order of each input list as ranking order.
2. For each memory, calculate:

```python
rrf_score += 1.0 / (rrf_k + rank)
```

Use 1-based ranks.

3. Preserve the best vector score and best text score per memory.
4. Return candidates sorted by descending `rrf_score`.
5. Limit to `limit`.

Pseudo-implementation:

```python
def reciprocal_rank_fusion(vector_results, text_results, *, rrf_k, limit):
    merged: dict[UUID, Candidate] = {}

    def add_results(results, attr_name):
        for rank, (memory, score) in enumerate(results, start=1):
            candidate = merged.get(memory.id)
            if candidate is None:
                candidate = Candidate(memory=memory)
                merged[memory.id] = candidate

            current = getattr(candidate, attr_name)
            if current is None or score > current:
                setattr(candidate, attr_name, score)

            candidate.rrf_score = (candidate.rrf_score or 0.0) + 1.0 / (rrf_k + rank)

    add_results(vector_results, "vector_score")
    add_results(text_results, "text_score")

    candidates = list(merged.values())
    candidates.sort(key=lambda c: c.rrf_score or 0.0, reverse=True)
    return candidates[:limit]
```

## Diversity filtering

Implement:

```python

    candidates: list[Candidate],
    *,
    similarity_threshold: float,
    max_results: int,
) -> list[Candidate]:
    ...
```

Behavior:

* Candidates are already sorted by final score.
* Keep a candidate if its embedding is not too similar to already kept candidates.
* Compare candidate memory embeddings using cosine similarity.
* If either embedding is missing, do not reject based on diversity.
* Stop when `max_results` is reached.

Pseudo:

```python
kept = []

for candidate in candidates:
    too_similar = False

    for existing in kept:
        if candidate.memory.embedding is None or existing.memory.embedding is None:
            continue

        similarity = cosine_similarity(
            list(candidate.memory.embedding),
            list(existing.memory.embedding),
        )

        if similarity >= similarity_threshold:
            too_similar = True
            break

    if not too_similar:
        kept.append(candidate)

    if len(kept) >= max_results:
        break

return kept
```

# 6. Upgrade `GraphStore`

Modify:

```text

```

Add neighbor expansion methods.

## `get_strong_neighbors`

```python
async def get_strong_neighbors(
    self,
    memory_ids: list[UUID],
    *,
    min_weight: float,
    limit_per_source: int,
) -> list[tuple[UUID, UUID, float]]:
    ...
```

Returns:

```text
(source_id, neighbor_id, weight)
```

Rules:

* For each memory ID, find edges where it is either source or target.
* The neighbor is the opposite side of the edge.
* Only edges with `weight >= min_weight`.
* Exclude neighbors already in `memory_ids`.
* Order by weight descending, then `last_co_accessed_at` descending.
* Limit per source.
* Avoid duplicate neighbor IDs globally; keep the strongest link if duplicate.

Implementation can use SQLAlchemy or raw SQL.

Suggested raw SQL logic:

```sql
WITH expanded AS (
    SELECT
        source_id AS anchor_id,
        target_id AS neighbor_id,
        weight,
        last_co_accessed_at
    FROM hebbian_edges
    WHERE source_id = ANY(:memory_ids)
      AND weight >= :min_weight

    UNION ALL

    SELECT
        target_id AS anchor_id,
        source_id AS neighbor_id,
        weight,
        last_co_accessed_at
    FROM hebbian_edges
    WHERE target_id = ANY(:memory_ids)
      AND weight >= :min_weight
),
ranked AS (
    SELECT
        anchor_id,
        neighbor_id,
        weight,
        row_number() OVER (
            PARTITION BY anchor_id
            ORDER BY weight DESC, last_co_accessed_at DESC
        ) AS rn
    FROM expanded
    WHERE neighbor_id != ALL(:memory_ids)
)
SELECT anchor_id, neighbor_id, weight
FROM ranked
WHERE rn <= :limit_per_source
ORDER BY weight DESC;
```

If array parameter typing is awkward with asyncpg, use SQLAlchemy `select()` and post-process in Python.

* Creates/increments every pair.

### Step 4 — Normalize RRF scores

Normalize candidate RRF scores so they are comparable to rerank scores:

```python
normalized_rrf = normalize_scores([c.rrf_score or 0.0 for c in candidates])

for candidate, score in zip(candidates, normalized_rrf):
    candidate.rrf_score = score
```

### Step 5 — LiteLLM rerank

If reranking is enabled:


Normalize rerank scores too:

```python

```

Assign:

```python

```

If reranking is disabled:

```python

```

### Step 6 — Relevance threshold

Determine relevance score:

```python
relevance_score = candidate.rerank_score if candidate.rerank_score is not None else candidate.rrf_score
```

Drop candidates where:

```python
relevance_score < settings.rerank_min_score
```

Only apply this threshold if reranking is enabled. If reranking is disabled, do not drop aggressively; use top candidates from RRF.

### Step 7 — Activation score

For each remaining candidate:

```python
activation = calculate_activation(
    base_importance=candidate.memory.base_importance,
    access_count=candidate.memory.access_count,
    last_accessed_at=candidate.memory.last_accessed_at,
    decay_rate=settings.decay_rate,
)
candidate.activation_score = activation
```

Normalize activation into a rough `[0, 1]` range for scoring:

```python
activation_for_score = min(activation / 1.5, 1.0)
```

### Step 8 — Final score

Normalize weights:

```python
total_weight = settings.recall_relevance_weight + settings.recall_activation_weight
relevance_weight = settings.recall_relevance_weight / total_weight
activation_weight = settings.recall_activation_weight / total_weight
```

Then:

```python
candidate.final_score = (
    relevance_weight * relevance_score
    + activation_weight * activation_for_score
)
```

Sort descending by `final_score`.

### Step 9 — Diversity pass

If enabled:

```python
primary = apply_diversity_filter(
    candidates,
    similarity_threshold=settings.diversity_similarity_threshold,
    max_results=top_k,
)
```

If disabled:

```python
primary = candidates[:top_k]
```

### Step 10 — Hebbian spreading

If enabled and `include_hebbian` is true:

1. Get primary IDs.
2. Query strong neighbors with edge weight threshold.
3. Fetch neighbor memories.
4. Convert them to `Candidate` objects with `source = "hebbian"`.
5. Do not rerank them.
6. Do not let them duplicate primary IDs.
7. Give them a final score based on edge strength and activation.

Suggested Hebbian score:

```python
edge_score = min(edge_weight / 10.0, 1.0)

activation = calculate_activation(...)

final_score = 0.6 * edge_score + 0.4 * min(activation / 1.5, 1.0)
```

Limit total Hebbian memories to `settings.hebbian_spread_limit`.

Important: keep primary results first, then Hebbian additions.

### Step 11 — Reinforcement

Returned memory IDs should include both primary and Hebbian memories.

If reinforcement enabled:

```python
await self.memory_store.mark_accessed(returned_ids)
await self.graph_store.reinforce_clique(
    returned_ids,
    increment=settings.reinforcement_edge_increment,
)
```

This keeps the memory network plastic.

### Step 12 — Return candidates

Return:

```python
primary + hebbian_candidates
```

Do not commit inside the service unless the Phase 1 pattern already does so. Prefer the route to commit.

```python
        candidates = self._score_activation_and_final(candidates)
        primary = self._select_primary(candidates, top_k)
        hebbian = await self._expand_hebbian(primary, include_hebbian)
        returned = primary + hebbian
        await self._reinforce(returned)
        return returned
```

This is much easier to evolve in Phase 3 and Phase 4.

---

# 14. Important design choice for Hebbian spreading

Hebbian results should **not** compete with primary results yet.

That means:

```text
primary results are selected first
Hebbian results are appended after
```

Do not let Hebbian expansion push out the directly relevant answer. Hebbian spreading is context enrichment, not a replacement for retrieval relevance.

Later, Phase 4 or Phase 5 can experiment with integrated graph activation scoring.
